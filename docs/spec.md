# 任意物体認証 検証ツール 仕様書

> ステータス: **ドラフト（策定中）**
> 最終更新: 2026-08-01

---

## 1. 概要

任意物体認証（Arbitrary Object Verification / Re-Identification）の性能を、
人手で対話的に検証するための GUI ツール。

画像群（動画フレーム列）を読み込み、ユーザーが GUI 上で **登録画像** と **照合画像** を
矩形（BBox）で切り出して指定すると、特徴抽出モデルで両者の embedding を求め、
**コサイン類似度**をスコアとして提示する。

「この物体とこの物体を、モデルは同一と判断するか？」を素早く試せることが目的。

### 1.1 想定する使い方

1. 画像フォルダを読み込む
2. あるフレームで対象物体を BBox で囲み、**登録画像**としてギャラリーに登録する
3. 別のフレームで対象物体を BBox で囲み、**照合画像**とする
4. ギャラリー全件とのスコアがランキング表示される。閾値により OK/NG も判定される
5. フレーム・BBox・モデル設定を変えながら 3〜4 を繰り返し、モデルの挙動を確かめる

---

## 2. 用語定義

| 用語 | 説明 |
|---|---|
| **画像群** | 検証対象となる連続画像。動画由来のフレーム列を想定 |
| **フレーム** | 画像群を構成する 1 枚の画像。任意サイズ |
| **BBox** | フレーム上に指定する矩形領域。切り出しの単位 |
| **登録画像 (Reference)** | 照合の基準となる物体画像。BBox で切り出される |
| **ギャラリー** | 登録画像の集合。1:N 照合の N 側 |
| **エントリ** | ギャラリーの 1 要素。1 つの物体を表し、1 枚以上の登録画像を持つ |
| **照合画像 (Query)** | ギャラリーと比較される物体画像。BBox で切り出される |
| **embedding** | モデルが出力する特徴ベクトル |
| **スコア** | embedding 同士のコサイン類似度。範囲 `[-1, 1]` |

## 3. 機能要件

### 3.1 データ入力

- 画像群を読み込める
- フレームは**任意サイズ**（統一されていなくてよい）
- **第 1 対応: 画像フォルダ**（フォルダ内の画像をファイル名順にフレーム列として扱う）
- **将来対応: 動画ファイル**（mp4 等）
  - 入力ソースは抽象化しておき、後から動画リーダーを追加できる構造とする

### 3.2 フレームビューア

- 読み込んだフレームを GUI 上に表示する
- 任意サイズの画像を扱うため、**ズーム・パン**が可能
- 現在のフレーム番号 / 総フレーム数 / ファイル名を表示

#### 3.2.1 再生モード

| モード | 操作 |
|---|---|
| **コマ送り** | ボタン / キー操作で 1 フレームずつ進む・戻る |
| **自動送り** | 再生・一時停止。再生速度（fps）を指定できる |
| **シーク** | スライダーで任意フレームへジャンプ |

### 3.3 BBox 指定

- **ユーザーがマウス操作で矩形を描画して BBox を決定できる**
- 描画後の調整（移動・リサイズ・削除）ができる
- 現在指定中の BBox がフレーム上に可視化される
- BBox は**由来（source）**を持つ: `manual`（手動描画） / `detector`（自動検出）
  - 自動検出は将来対応（7.1 参照）。データ構造は最初から由来を持たせておく
- **枠の形状**
  - **デフォルトは正方形**（アスペクト比 1:1 に拘束して描画・リサイズ）
  - **長方形（自由アスペクト）にも切り替えられる**
  - 切り替えは GUI 上のトグルで行う

### 3.4 登録画像の指定

登録画像は以下のいずれの方法でも設定できる:

- **A. 事前設定** — あらかじめ用意した画像ファイルを登録画像として読み込む
- **B. 画像群から取得** — 読み込んだ画像群の任意のフレーム上で BBox を描いて登録する

どちらを使うかは **GUI 上で指定できる**こと。

### 3.5 照合画像の指定

- 入力画像（現在表示中のフレーム）上で BBox を描いて切り出す

### 3.6 ギャラリー（1:N 照合）

- 登録画像は**複数保持できる**
- 1 回の照合で、照合画像を**ギャラリー内の全エントリと比較**し、
  スコアの降順でランキング表示する
- 1:1 照合は「エントリが 1 件の 1:N 照合」として同一機構で扱う

#### 3.6.1 エントリの構造

各エントリは以下を持つ:

- ID / ラベル（ユーザーが任意に付与）
- **1 枚以上の登録画像**（マルチビュー対応。別角度・別フレームを登録できる）
- 各登録画像の由来（事前設定ファイル / フレーム番号 + BBox 座標）
- 各登録画像の embedding（抽出済みのものをキャッシュ）

#### 3.6.2 マルチビュー時のスコア集約

エントリが複数の登録画像を持つ場合、エントリのスコアは以下から**選択できる**:

| 方式 | 定義 |
|---|---|
| **max** | 各登録画像とのスコアの最大値 |
| **mean** | 各登録画像とのスコアの平均値 |

- GUI 上で切替可能。デフォルトは **max**

#### 3.6.3 操作

- エントリの追加・削除・リネーム
- エントリへの登録画像の追加・削除

### 3.7 前処理

BBox で切り出した領域をモデル入力サイズに変換する手順:

1. BBox 領域をフレームから切り出す
2. **アスペクト比を維持**したまま、**長辺**が入力サイズになるようリサイズ
3. 短辺側の余白を**黒でパディング**して正方形にする（レターボックス）
4. 正規化（mean / std）を適用

- 入力サイズ・正規化パラメータは**モデル定義から取得**する（モデルごとに異なるため）
- 枠が正方形の場合、パディングは実質発生しない
- パディング色は黒固定（将来的に設定可能としてもよい）

### 3.8 モデル（差し替え可能な特徴抽出）

**DINOv2 固定にしない。** 任意のモデルを読み込んで検証できることを要件とする。

- モデルは**パスを指定して読み込む**
- モデル形式ごとに**ローダ**を用意し、ローダを追加すれば新しい形式に対応できる
- DINOv2 は「標準で同梱されるローダ + 既定エントリ」という位置づけ

#### 3.8.1 特徴抽出インタフェース

すべてのモデルは共通インタフェースの背後に隠蔽される。

```python
class FeatureExtractor(Protocol):
    # 前処理に必要な情報
    input_size: int                  # 入力の一辺（px）
    mean: tuple[float, float, float] # 正規化 mean
    std:  tuple[float, float, float] # 正規化 std

    # このモデルが対応する embedding 種別
    supported_embeddings: list[str]  # 例: ["cls", "patch_mean", "concat"]

    def embed(
        self,
        images: np.ndarray,          # (N, H, W, 3) uint8 RGB, 前処理済み
        embedding_type: str,
    ) -> np.ndarray:                 # (N, D) float32
        ...
```

GUI・スコア算出・ギャラリーはこのインタフェースのみに依存し、
モデルの実体を知らない。

#### 3.8.2 ローダ機構

モデル形式ごとにローダを実装し、**レジストリに登録**する。

```python
@register_loader("torchscript")
class TorchScriptLoader(ModelLoader):
    def load(self, path: str, config: dict) -> FeatureExtractor: ...
```

標準で用意するローダ:

| ローダ名 | 対象 | 備考 |
|---|---|---|
| `torch_hub` | torch.hub 経由のモデル | DINOv2 の既定ロード方法 |
| `timm` | timm のモデル + 重みファイル | ViT 系全般 |
| `huggingface` | transformers の `AutoModel`（ローカルディレクトリ / Hub ID） | |
| `torchscript` | `.pt` / `.pth`（TorchScript） | |
| `onnx` | `.onnx` | onnxruntime |

- **ローダの追加のみで新形式に対応できる**こと（GUI 側の変更を要さない）
- ユーザーが独自ローダを追加できるよう、
  所定のディレクトリに置いた Python ファイルを起動時に読み込む仕組みを設ける

#### 3.8.3 モデルレジストリ

利用可能なモデルを設定ファイル（YAML）で管理し、GUI から選択できるようにする。

```yaml
# models/registry.yaml
models:
  - name: dinov2_vitb14          # GUI に表示される名前
    loader: torch_hub
    args:
      repo: facebookresearch/dinov2
      model: dinov2_vitb14
    preprocess:
      input_size: 224
      mean: [0.485, 0.456, 0.406]
      std:  [0.229, 0.224, 0.225]
    embeddings: [cls, patch_mean, concat]

  - name: my_model
    loader: torchscript
    args:
      path: /path/to/model.pt
    preprocess:
      input_size: 256
      mean: [0.5, 0.5, 0.5]
      std:  [0.5, 0.5, 0.5]
    embeddings: [output]
```

GUI 上でできること:

- レジストリのモデルをドロップダウンから選択して読み込む
- **モデルを新規追加**する（パス指定 + ローダ選択 + 前処理パラメータ入力）
  → レジストリに追記され、次回以降も選べる
- 現在ロード中のモデル名・デバイス・embedding 次元数を表示

#### 3.8.4 embedding の取り方

モデルが対応する種別を **GUI 上で切替可能**とする。

| 方式 | 説明 |
|---|---|
| **cls** | CLS トークン。画像全体を要約したベクトル |
| **patch_mean** | 全パッチトークンの平均 |
| **concat** | 上記 2 つを連結 |
| **output** | モデルの出力をそのまま使う（ViT 以外・エクスポート済みモデル向け） |

- ViT 系以外は `output` のみ対応、といったケースを許容する
- GUI は `supported_embeddings` に応じて選択肢を出し分ける

#### 3.8.5 既定モデル

- **DINOv2 ViT-B/14**（`torch_hub` ローダ）をレジストリの既定エントリとして同梱する
- ViT-S / ViT-L も既定エントリに含める
- 既定の embedding 種別は **cls**

### 3.9 スコア算出と判定

- embedding を L2 正規化し、**コサイン類似度**をスコアとする
- **閾値**を GUI 上で設定できる（スライダー等）
- スコアが閾値以上なら **OK**、未満なら **NG** として判定結果を表示する
- 閾値はランキング表示上でも視覚的に分かるようにする（色分け、区切り線等）

### 3.10 結果表示

- 照合画像のサムネイルを表示
- ギャラリー各エントリのサムネイルとスコアを、**スコア降順のランキング**で表示
- 各エントリに OK/NG 判定を併記

### 3.11 結果の保存（将来対応）

- 現時点では必須ではない
- 後から CSV 等での出力を追加できるよう、
  照合結果を構造化データとして保持する設計としておく

### 3.12 セッション管理

**名前付きセッション + 自動保存**の併用とする。

```
<プロジェクト>/sessions/
├── _autosave.json          # 作業中に随時上書き。起動時に自動復元
├── car_test.json           # 「名前を付けて保存」したもの
└── bottle_multiview.json
```

- 作業中の状態は `_autosave.json` に随時保存する（クラッシュ時の損失を防ぐ）
- 「名前を付けて保存」で任意の名前のセッションを作れる
- 「開く」で過去のセッションを指定して再現できる

#### 3.12.1 保存する内容

| 項目 | 内容 |
|---|---|
| 画像フォルダ | パスのみ（画像はコピーしない） |
| ギャラリー | エントリ名、各登録画像の由来（フレーム番号 or ファイルパス）、BBox 座標、枠形状 |
| 照合画像 | 最後に指定したフレーム番号と BBox |
| モデル設定 | モデル名（レジストリのキー）、embedding 種別 |
| スコア設定 | 集約方式（max / mean）、閾値 |
| 表示状態 | 現在のフレーム番号 |

- **embedding は保存しない**。読み込み時に再計算する
  （モデルや設定が変われば結果も変わるべきため）

## 4. 技術スタック

| 項目 | 選定 | 備考 |
|---|---|---|
| 言語 | Python | |
| 環境管理 | **uv** | 使い回しやすさ重視 |
| GUI | **imgui-bundle** | Dear ImGui + immvision + ImPlot + portable-file-dialogs |
| モデル | **任意**（パス指定 + ローダ機構） | 既定は DINOv2 ViT-B/14 |
| 数値計算 | PyTorch | ONNX ローダ利用時は onnxruntime も |
| 設定ファイル | YAML | モデルレジストリ |
| セッション | JSON | |
| 実行デバイス | 自動判定 | `cuda` > `mps` > `cpu` の順。GUI 上で表示・手動切替も可 |

### 4.1 設計方針

- **GUI とロジックを分離**し、特徴抽出・スコア算出は CLI やテストからも呼べるようにする
- **モデルは差し替え前提**。GUI は `FeatureExtractor` インタフェースのみに依存し、
  モデル形式への対応はローダの追加だけで完結する
- 入力ソース（画像フォルダ / 動画）も抽象化する
- embedding はキャッシュし、同じ BBox の再計算を避ける
  （キャッシュキーにモデル名と embedding 種別を含める）

## 7. 将来拡張

実装は後回しとするが、**現在の設計がこれらを阻害しないこと**を要件とする。

### 7.1 検出モデルによる BBox の自動生成

手動描画に加えて、検出モデルで BBox 候補を自動生成できるようにする。

**想定する動作**

1. 現在のフレームに対して検出モデルを実行する
2. 検出された候補 BBox をフレーム上にオーバーレイ表示する
3. ユーザーが候補をクリックして照合画像 / 登録画像として採用する
4. 採用後は手動 BBox と同様に微調整できる

**設計上の要件（今から満たしておく）**

- BBox は `source` フィールドを持ち、`manual` / `detector` を区別できる
- 検出モデルも**特徴抽出モデルと同じローダ／レジストリ機構**に載せる
  - ただしインタフェースは別（`Detector`）

```python
class Detector(Protocol):
    def detect(self, image: np.ndarray) -> list[Detection]:
        ...   # Detection: bbox, score, (任意で) label
```

- 特徴抽出モデルと検出モデルは**独立して選択・ロード**できる
- 任意物体を対象とするため、クラス非依存（class-agnostic）または
  オープン語彙の検出モデルを想定する

### 7.2 動画ファイルの直接読み込み

- 入力ソース抽象化により、動画リーダーの追加で対応する（3.1 参照）

### 7.3 検証結果のエクスポート

- 照合結果を CSV 等で出力する（3.11 参照）

### 7.4 フレーム間の追跡

- 7.1 の検出と組み合わせ、自動送り再生中に対象を追跡しながら
  連続的にスコアを算出する

> 7.4 は要望として挙がっていないが、7.1 の自然な延長として想定される。
> 実装するかは未定。
